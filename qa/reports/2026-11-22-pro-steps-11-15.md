## Product owner summary

**What I tested:**
- **The Pro window:** opening it before and after connecting, the safety notice, the "game not running" poll on a real worker thread, and closing and reopening it. Closing with frozen addresses, from Pro and from the main window.
- **Cheats tab and cave editor:**
  - drafts and Build, the read-only editor while a cheat is on
  - a Build racing with a tick in My cheats (forced with real threads)
  - typing during a Build, and list refreshes while typing
- **On/off:**
  - My cheats ticks for Pro cheats
  - "Edit in Pro" on guided cheats, including freeze cheats
  - a Refresh while a Pro cheat is on
- **Import:** Convert to assembly when the assembler fails, and a file for another game.
- **Code view:** marks, "show original", follow, back and forward, and stale pages.
- **Memory view:** unknown bytes at a map edge, the inspector, and the order of page loads.
- **Scanner:** who owns the console's search when a guided search starts during a Pro scan (forced with real threads), refused values, and stale page loads.
- **Address list:** freezes, typed values on frozen rows, and pausing when the game is gone.
- **Liveness change:** that it leaves the guided console paths alone (the NG socket lock on guided worker threads, and the thread-local limit never leaking across pool threads).

**Verdict:** the window, the views and the review fixes mostly work as specified. All 3349 existing tests still pass, and the liveness change doesn't affect the guided paths. I found three serious on/off problems, where the game and the app disagree about whether a Pro cheat is on.

**Bugs:** 12 in total.

| Severity | Count |
|---|---|
| Critical | 0 |
| High | 3 |
| Medium | 3 |

**Most important problems:**
- **BUG-01 (High):** if a Pro cheat is ticked in My cheats while its Build is still running, Pro then records the new cave as on, but the game is running the old one.
- **BUG-02 (High):** "Edit in Pro" on a guided freeze cheat breaks it.
  - Turning it on writes the value into the game, then fails with an error.
  - The cheat shows Off, and it can't be turned on (or off) again.
- **BUG-03 (High):** after Refresh from the PS5 home screen, a Pro cheat that is on shows Off but keeps running in the game.
  - The app then refuses to turn it on ("code isn't what the cheat expects"), so the player can't switch it off until the game restarts.
  - The same happens after restarting the app while the game runs.
- **BUG-04 (Medium):** two guided searches (the percent search and Find it again's class search) don't take the new search lock. If one starts while a Pro scan starts, it can end up reading the Pro scan's results.
- **BUG-05 (Medium):** text typed in the cave editor while a Build runs is silently thrown away when the Build finishes.
- **BUG-06 (Medium):** the Code view doesn't re-read the game after a cheat is turned on or off. It shows "(on)" next to the old, unpatched instruction.

**Release recommendation:** ⚠️ **Not ready for the three High bugs; ready with known issues once they are fixed.** The Medium and Low bugs have workarounds (press Go again, wait for Build to finish, retry) and can ship as known issues.

## Bugs

### BUG-01: A Build that finishes after the cheat was ticked on in My cheats records new cave bytes the game doesn't have
- Severity: High
- Priority: P1
- Related test case: TC-10
- Automated test: `tests/qa/test_pro_steps_11_15_qa.py::test_bug01_build_never_changes_a_cheat_that_went_on_meanwhile`
- Environment: `1de30ca`, Linux, Python 3.13.18, PySide6 6.12.0. The Pro TaskRunner is on Qt's thread pool, as in the app.
- Steps to reproduce:
  1. Create a Pro cave cheat.
  2. Type a new source and press Build. The build runs on the worker.
  3. Before it ends, tick the same cheat in My cheats (main window).
  4. Let the build finish.
- Test data: new source `nop / nop / nop / original / jmp return` (18 bytes); the old cave is 15 bytes.
- Expected result: Pro never changes a cheat while it is on (spec PR-8: Build is refused while on, `TURN_OFF_FIRST`). The cheat's recorded bytes must equal what the game runs. Either the tick waits or is refused while Pro works on that cheat, or the build result is dropped with a message.
- Actual result:
  - The cheat is On.
  - `entry.cave_bytes` is the new `909090c4c17a…e908c2ffff`.
  - The game holds the old `c4c17a118c24ac020000e90bc2ffff000000`.
  - The status says "Built Infinite health: 18 bytes at +0x3ef0."
  - Later live variable writes (AC-8.7) use the new layout's offsets against the old cave in the game.
- Evidence: `old c4c17a118c24ac020000e90bc2ffff new 909090c4c17a118c24ac020000e908c2ffff enabled True / ingame c4c17a118c24ac020000e90bc2ffff000000`
- Suspected cause:
  - `ui/pro/cheats_tab.py:396-426` (`build_entry`): the `c.enabled` check happens only on click, and `done` applies `_apply(pc, built)` without checking again.
  - `ui/cheats_view.py:353-361` (`_turn_on`) doesn't know the Pro tab is busy with that cheat.
  - The same pattern is in `add_entry_at` (`done`, line 533) and `_set_value` (`on` is captured at click, line 664).
- Impact for the product owner: a player who ticks a cheat while it is still building can end up with the game running different code from what the app shows. A later value change can then write into the wrong place in the game's code and crash it.

### BUG-02: Edit in Pro on a guided freeze cheat: turning it on writes the value, then fails; the cheat shows Off and is stuck
- Severity: High
- Priority: P1
- Related test case: TC-13
- Automated test: `test_bug02_adopted_freeze_cheat_turns_on_or_writes_nothing[pro|my_cheats]`
- Environment: as above (sync runner).
- Steps to reproduce:
  1. Have a guided cheat on a static module value with "keep it at" (freeze=True). This is the badge's CheatRunner "written once" case.
  2. In Pro's Cheats tab, select it and press Edit in Pro. It is adopted.
  3. Tick On, in Pro or in My cheats.
- Test data: MODULE_VALUE at `eboot.bin+0x4100`, on `63000000`, off `00000000`, freeze=True.
- Expected result: the cheat goes on, or nothing is written and the player is told why (AC-8.4: "Then … the cheat shows On"; a failure must change nothing). Adopting a freeze cheat should be refused, or the freeze dropped with a note, because Pro can't freeze.
- Actual result:
  - `compile.enable` writes `63000000` into the game.
  - Then `LiveCheats.mark_on` raises `ValueError: a kept fix never freezes`.
  - **Pro tab:** the exception escapes the Qt slot, the tab's buttons are not refreshed, and the status is empty.
  - **My cheats:** the generic error path runs.
  - In both, the cheat shows Off but the game holds the value.
  - Ticking On again is refused with SiteChanged, because the site holds the on-bytes. The cheat can't be turned off either, because it is "off".
- Evidence: `ValueError: a kept fix never freezes` from `cheats_tab.py:573 done -> freezer.py:291 mark_on`. The game holds `63000000` afterwards.
- Suspected cause:
  - `core/pro/asm_text.py:296-304` (`adopt`) accepts freeze cheats.
  - `core/pro/compile.py:163-169` (`refresh`) never clears `Cheat.freeze`.
  - `cheats_tab.py:572-574` and `cheats_view.py:360-361` call `mark_on` after the bytes are written. `mark_on` raises for `freeze` (`core/freezer.py:287-291`).
- Impact for the product owner: a player who moves a "keep it at" cheat into Pro and turns it on gets an error. The cheat is then secretly active in the game and can't be switched off.

### BUG-03: After a Refresh that keeps the game process, a Pro cheat that is on shows Off and can't be turned on or off
- Severity: High
- Priority: P1
- Related test case: TC-14 (and TC-30)
- Automated test: `test_bug03_pro_cheat_still_in_the_game_after_refresh_can_be_turned_off`
- Environment: as above.
- Steps to reproduce:
  1. Turn a Pro cave cheat on.
  2. Go to the PS5 home screen. The game stays suspended with the same PID, and the version can't be read.
  3. Press Refresh in the main window.
  4. Tick the cheat on again, in Pro or in My cheats.
- Test data: `fakegame` 1; `foreground_pid=None` gives GameInfo with version `unknown` and the same PID 31.
- Expected result: the app's on/off state matches the game. The cheat stays On (same process, bytes still there), or ticking it on accepts sites that already hold the cheat's own bytes. The player must always be able to turn a running cheat off.
- Actual result:
  - `Controller._on_game` marks every cheat off.
  - The game still holds the jump (`e9…`) and the cave.
  - Ticking On is refused with "The game's code at 0x400100 isn't what this cheat expects (expected c4 c1 7a…, found e9 eb 3d 00 00 90…). Nothing was changed."
  - No path turns it off.
  - The same happens after closing and reopening the app while the game keeps running, because closing leaves cheats in the game (TC-30).
- Evidence: `enabled False jump e9`, then `enabled2 False status The game's code at 0x400100 isn't what this cheat expects …`.
- Suspected cause:
  - `ui/controller.py:95-104` calls `live.mark_all_off()` on any GameInfo change, even with the same PID. find_again's `on_game` already treats the same process as keeping its hooks.
  - `core/pro/compile.py:461-467` (`enable`) treats a jump/bytes site that holds its on-bytes as changed (only caves may hold their on-bytes).
- Impact for the product owner: after pressing Refresh at the PS5 home screen, or after restarting the app, a Pro cheat keeps running in the game. The app says it's off and won't let the player switch it off until the game is restarted.

### BUG-04: The guided percent search and Find it again's class search start a console search without `Session.search_lock`
- Severity: Medium
- Priority: P2
- Related test case: TC-24
- Automated test: `test_bug04_every_guided_search_start_honours_the_search_lock[percent|class_search]`
- Environment: as above, real threads.
- Steps to reproduce:
  1. A Pro first scan has claimed the search. On its worker, under `search_lock`, it has checked it is the owner and is about to call `scan_start`.
  2. A guided percent search (`Scanner.percent_scan`) or Find it again's class search (`vtable_find.find_by_vtable`) starts on another worker.
- Test data: Pro EXACT int32 100; guided 50 %; class search on `PLAYER_VT`.
- Expected result: per the review design ("Held around 'is it still mine?' plus the console call, by the guided Scanner and the Pro scanner"), the guided search waits for the lock. Its `scan_start` runs after the Pro one, so the owner (guided) and the console's search agree. The plain guided value search does this (TC-23 passes).
- Actual result: the order is `['guided', 'pro']`. The guided search's `scan_start` runs first, then Pro's. `search_owner` is the guided Scanner, but the console holds the Pro search, so the guided next scan or results read the Pro search. `find_by_vtable` also calls `scan_cancel()` in its `finally`, which can cancel a search it doesn't own.
- Evidence: `order ['guided', 'pro'] owner <cheatmaker.core.scanner.Scanner …>`
- Suspected cause:
  - `core/scanner.py:464-475` (`_percent_first`) sets `search_owner = self` and calls `scan_start` outside `search_lock`.
  - `core/vtable_find.py:40-55` calls `take_search()`, `scan_start`, `scan_results` and `scan_cancel` without the lock.
  - (`_percent_pc` and `_note_percent` also use `scan_results`, `scan_restrict` and `scan_rebase` without an owner check. That is fine while `active` gates them, but worth wrapping too.)
- Impact for the product owner: rarely, if the player starts a guided percent search or Find it again while a Pro scan is starting, the guided search shows the Pro scan's matches, and the player may lock the wrong value.

### BUG-05: The cave editor stays editable during a Build; text typed meanwhile is thrown away, and Build can run twice
- Severity: Medium
- Priority: P2
- Related test case: TC-11
- Automated test: `test_bug05_typing_during_a_build_is_kept`
- Environment: as above, real threads.
- Steps to reproduce:
  1. Type source A and press Build.
  2. While it runs, type source B.
  3. Let the build finish.
- Expected result: the editor is locked while building, or B stays as a draft (the review-fix rule: "the draft becomes the source only after a successful Build", which here was A).
- Actual result:
  - Source is A, and the editor shows A. B is gone with no message.

- Impact for the product owner: a player who keeps typing while Build runs (NASM takes a moment) silently loses what they typed.

- Environment: `c963c4e`, as above.
- Steps to reproduce (a): in My cheats, untick a Pro cave cheat, tick it within 0.5 s, then untick it again.
