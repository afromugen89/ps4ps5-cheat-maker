## Product owner summary

**What I tested:**
- The Pro scanner model: unsigned types, "greater than" / "less than", previous and first values, and paging. This covered the ends of every type, decimals (including tiny and huge ones, infinity and NaN in memory), console snapshots and several types at once.
- `.cmproj` format 5: format 4 files load and save, newer formats are refused, and broken Pro entries are handled.
- The CheatRunner / PC only badge, and that the cheat file holds exactly the same cheats as before.
- `.mc4`: export and import round trip, special characters, UTF-16, padding variants, and 600 broken files.
- The NASM fetch tool and where the app looks for NASM.
- Guided regressions: `.shn` and `.json` bytes compared against `origin/main`.

**Verdict:** the core of these five steps is solid.
- Guided cheat files are byte for byte the same as on main. This holds for every golden fixture, for the same files with `& < > "` in the title, credits and names, and for a mixed set of guided cheats (frozen static values, Player only with an editable value, heap, found again, Lock it, empty and combined).
- Greater/less as a console range keeps exactly the values the PC compare keeps, for every type and at every type end.
- The real client and FakeConsole agree on greater/less narrowing across 30 randomised runs (snapshot, PC-side and multi-type).
- mc4 equals the sanitised `.shn` byte for byte on every fixture (AC-12.2). Garbage input only ever gives the normal "can't read" error.
- The badge's export set equals the old "saveable" set for all 56 guided cheat shapes tested.

**Bugs:** 0 Critical, 1 High, 0 Medium, 3 Low.

- BUG-01 (High): a notes file (`.cmproj`) with a Pro variable too large for its type, e.g. a 4-byte decimal of 1e39, crashes the load instead of showing "can't be read". The file is then **overwritten** by the next save, with no `.bak` kept, so the player's notes for that game are lost. This needs a hand-edited or damaged file today, but a later Pro editor could write one.
- BUG-02 (Low): "greater than" / "less than" with a number of more than about 309 digits raises an internal OverflowError instead of keeping all or nothing.
- BUG-03 (Low): an `.mc4` saved with a UTF-8 BOM (e.g. re-saved in Notepad) is refused as "not an mc4 file".
- BUG-04 (Low): a GoldHEN `.json` saved as UTF-16 is now reported as "not valid XML". Before, it said "not valid JSON". It is refused either way.

**Release recommendation: ⚠️ Ready with known issues.** BUG-01 should be fixed before step 8 (the Pro cheat editor) writes variables. The fix is small: treat OverflowError as a bad value. The Low bugs can wait.

## Scope

In scope: everything listed above, i.e. steps 1-5 of architecture-pro and the guided regressions they could cause.

Out of scope: the Pro window and every Pro UI (steps 6+); real-console behaviour (C-P2: NG unsigned type ids, the TURBOSCAN_GET offset field and the order of the 3-value rows; S-P8: how CheatRunner shows mc4 names); running the real `fetch_nasm.py` download (the hash is not pinned, by design).

Risk areas: money-like values at type ends (wrong matches), losing the player's notes (format change), changing guided cheat files, and reading untrusted cheat files.

## Bugs

### BUG-01: An out-of-range Pro variable crashes the notes load, and the notes file is then overwritten
- Severity: High (data loss of the game's notes; the trigger needs a hand-edited or damaged file today)
- Priority: P2 (before step 8 writes variables)
- Related test case: TC-23, TC-24 | Automated tests: `tests/qa/test_pro_steps_1_5_qa.py::test_bug01_out_of_range_variable_is_a_project_file_error` (3 cases), `::test_bug01_variable_constructor_raises_value_error`, `::test_bug01_notes_with_an_out_of_range_variable_survive_in_the_app`
- Environment: b19554a, Linux, Python 3.13.18
- Steps to reproduce: 1. Put a `.cmproj` for the connected game whose `pro_cheats` has `{"name": "mult", "type": "float", "value": 1e39}` (or `"type": "int64", "value": <400-digit int>`). 2. Connect. 3. Make any cheat that saves notes (e.g. Find it next time).
- Expected result: "can't be read" is shown, and the file is set aside before a new one is saved (the existing `set_aside` rule; spec-pro §5; implementation notes: "bad files raise ValueError, so project.load reports ProjectFileError as before").
- Actual result: `OverflowError: float too large to pack with f format` is raised in the Qt event loop. `project.load` only catches `(OSError, ValueError, KeyError, TypeError, IndexError, AttributeError)`, so `_unreadable` is never set, and the next save overwrites the file. No `.bak` copy is left.
- Evidence: `Variable("mult", ValueType.FLOAT, 5e38)` → `OverflowError`; `Variable("big", ValueType.INT64, 10**400)` → `OverflowError: int too large to convert to float`. In the UI test, the directory holds no file with the original content afterwards.
- Suspected cause: `src/cheatmaker/core/pro/model.py:89` (`float(self.value).is_integer()`) and `:91` (`self.encoded()`), which reaches `ValueType.encode` at `core/values.py:40` (`struct.pack('<f', 1e39)` raises OverflowError). The docstring says "Raises ValueError". Fix in `Variable.__post_init__` (turn OverflowError into ValueError), or have `project.load` also catch OverflowError/ArithmeticError.
- Impact for the product owner: a damaged notes file for one game is silently replaced, and everything Cheat Maker had learned about that game is lost.

### BUG-02: Greater/less than with a number past the float range raises OverflowError
- Severity: Low
- Priority: P3
- Related test case: TC-05 | Automated test: `tests/qa/test_pro_steps_1_5_qa.py::test_bug02_greater_less_with_a_huge_whole_number` (4 cases)
- Environment: b19554a
- Steps to reproduce: `as_between(ValueType.FLOAT, Compare.LESS, 10**400)`. The same happens with `value_for`, which every scan path calls. `parse_number("1" + "0"*400)` accepts the text.
- Expected result: LESS keeps every finite value, `(-F32_MAX, F32_MAX)`; GREATER keeps nothing (`None`). This is the "type ends" rule in the implementation notes: "clamped to the finite range, or None when nothing can match".
- Actual result: `OverflowError: int too large to convert to float` (values.py:230, `v = float(value)`).
- Suspected cause: `float(value)` on a Python int beyond about 1.8e308. Whole-number types are fine (`math.floor` on ints).
- Impact for the product owner: typing an absurdly long number in the Pro scanner would show an internal error instead of "nothing found". Once the Pro scanner UI exists, only someone pasting a huge number would see it.

### BUG-03: An .mc4 with a UTF-8 BOM is refused
- Severity: Low
- Priority: P3
- Related test case: TC-58 | Automated test: `tests/qa/test_pro_steps_1_5_qa.py::test_bug03_mc4_with_a_utf8_bom_is_read`
- Environment: b19554a
- Steps to reproduce: export an mc4, prepend `EF BB BF` (as Notepad's "UTF-8 with BOM" does), then `formats.load_path` it.
- Expected result: it loads. `sniff` already strips BOMs for shn/json, and spec PR-14 asks for mc4 import.
- Actual result: `CheatFileError: not an mc4 file (base64): Only base64 data is allowed`
- Suspected cause: `src/cheatmaker/formats/mc4.py:43`, which strips only whitespace before `b64decode(validate=True)`.
- Impact for the product owner: a cheat file someone opened and re-saved in a text editor can't be imported.

### BUG-04: A UTF-16 .json is now reported as "not valid XML"
- Severity: Low
- Priority: P3
- Related test case: TC-59 | Automated test: `tests/qa/test_pro_steps_1_5_qa.py::test_bug04_utf16_json_error_names_json`
- Environment: b19554a vs origin/main
- Steps to reproduce: save a GoldHEN `.json` as UTF-16 (with a BOM), then `formats.load_path` it.
- Expected result: a JSON error as before: main says `not valid JSON: 'utf-8' codec can't decode byte 0xff ...`. Better still, it could load.
- Actual result: `CheatFileError: not valid XML: not well-formed (invalid token): line 1, column 0`
- Suspected cause: `src/cheatmaker/formats/__init__.py:29`. `sniff` returns "shn" for any UTF-16 BOM ("real UTF-16 is only ever .shn") without looking at the content after the BOM.
- Impact for the product owner: a confusing message that mentions XML for a JSON file.

## Observations (not filed)

- A control character in a name or title (newline, tab, CR) is still written as `&#10;` / `&#9;` / `&#13;` in mc4, so an `&` can appear there. AC-12.4 only names `& < > "`, so this is not a bug. It is worth adding to S-P8 ("older readers un-escape blindly"). In practice only an imported file can carry such a name.
- `badge()` and `Cheat.saveable` can differ for a shape guided mode never builds: a cheat with `cheat.anchor` set but only module locations. `saveable` says yes, the badge says PC only (found again), and the export would drop it. Every anchored cheat the app makes holds a SESSION_ADDRESS line, so the sets are equal in practice (TC-30).
- `ProEntry` accepts offsets beyond 64 bits (e.g. 2^70), and variable names that are NASM keywords or registers (`rax`, `byte`). Both will fail later, in compile and assemble. Worth checking in step 6.
- A pre-existing difference, not Pro: the real client's CHANGED/UNCHANGED on a float snapshot keeps NaN/inf cells, which FakeConsole drops. EXACT with an out-of-range number on a snapshot raises ValueError on the real client but gives 0 on FakeConsole.
- On Windows, `shutil.which` also searches the current folder. A `nasm.exe` placed in the app's working folder would be used when there is no configured or bundled copy. The risk is low, since the bundled copy comes first.

## Not tested / risks

- Real-console behaviour (C-P2): NG unsigned type ids 0/2/4/6, the TURBOSCAN_GET `offset` field, and the order of the 3-value rows. These are documented as unverified. FakeNgServer implements the assumed layout, so these tests can't catch a wrong assumption.
- CheatRunner's handling of mc4 (S-P8) and loading a ReaperPy-made mc4 (no fixture yet).
- The real NASM download and hash (not pinned, by design; CI step is `continue-on-error`).
- No Pro UI exists yet. AC-S2 hover text was checked only through `Badge.tooltip` and the save dialog tooltip.
