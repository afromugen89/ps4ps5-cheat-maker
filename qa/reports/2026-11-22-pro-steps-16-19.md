## Bugs

### BUG-01: "What does it access?" and the guided Player only collect share one table
- Severity: Medium
- Priority: P2
- Related test case: TC-33 | Automated test: `tests/qa/test_pro_steps_16_19_qa.py::test_bug01_a_guided_collect_cant_take_the_table_a_sample_is_using`
- Environment: a6558f1 and HEAD, Linux, Python 3.13, fake game
- Steps to reproduce:
  1. Pro > Watch > What does it access? on the health writer (it only runs when the player is hit, so the table stays empty between hits).
  2. While it samples, in the main window run Make it work (Only me / Player only) or Lock it > Player only on another value.
- Test data: `fg.build(1)`, sampler on `fg.WRITER`; `cv.find_table` called during the sample.
- Expected result: the guided collect gets its own table or is refused while a sample runs (AC-3.4: the sampler's table is its own and is cleared at the end; guided Player only must "behave exactly as before").
- Actual result: `cv.find_table` hands the guided step the very table the sampler uses (`0x404e00` both times). The sampler zeroes it every 0.25 s and reads every entry, so Make it work's collect (which reads the table once at the end) sees few or none of its objects, and the sample lists the guided writer's objects as accesses of its instruction.
- Evidence: probe output `sampler table 0x404e00 found during sample 0x404e00`.
- Suspected cause: `core/cave.py:688 find_table` always picks the last `TABLE_SIZE` bytes of module data and only checks they are zero; `access_sampler.sample` (and `cave.collect_objects`, `builder._collect`) take no lock. Fix ideas: a `Session` claim for the table (like `claim_debugger`), or the sampler adds its table to `session.reserved_rooms` while it runs and `find_table` skips reserved rooms.
- Impact for the product owner: if a player samples in Pro while Make it work picks "only me", Make it work can choose the wrong characters (or none), and the Pro list shows addresses its instruction never touched.

### BUG-02: the firewall message can come 2 s after the 10 s deadline
- Severity: Low
- Priority: P3
- Related test case: TC-05 | Automated test: `test_bug02_firewall_said_within_the_deadline_when_the_ps5_is_silent`
- Environment: a6558f1 and HEAD
- Steps to reproduce: 1. A server that accepts connections on the debugger port and never answers (neither DEBUG_ATTACH nor the fresh-connection DEBUG_DETACH). 2. `DebugSession(..., deadline=0.5).attach()`.
- Expected result: FirewallBlocked within the deadline (AC-1.3 "says so within 10 s"; console test C-P3b "within 10 s of Start").
- Actual result: FirewallBlocked after 2.5 s for a 0.5 s deadline; with the real deadline that is up to 12 s (plus thread joins).
- Evidence: `took 2.5 conns 2` (probe), the test asserts `took <= deadline + 0.75`.
- Suspected cause: `debugger.py _close -> _detach_fresh` runs before the error is raised and waits `FRESH_DETACH_TIMEOUT` (2 s) for the detach answer. Either start the detach 2 s before the deadline, or raise first and detach on a background thread.
- Impact for the product owner: on a PC with the firewall on, the message may take 12 s instead of 10 s. Also affects console test C-P3e's "within 10 s".

### BUG-03: a write/access watch stops after 16 identical hits as "repeating"
- Severity: Medium
- Priority: P2
- Related test case: TC-14 | Automated test: `test_tc14_a_game_writing_the_same_value_every_frame_is_not_a_repeat` (regular test: fails on a6558f1, passes on the follow-up)
- Environment: a6558f1
- Steps to reproduce: 1. Watch health (Writes). 2. The game writes it every frame from one instruction with the same registers (the same value, the same object), or a thread spins reading a flag (Accesses). 3. Wait for 16 hits.
- Expected result: a data watch traps after the instruction and can't re-fire without the game moving on; it runs on to 60 s / 500 hits (AC-3.2, PR-3).
- Actual result: `ended=repeats` after 16 hits with "The watch fired 16 times in a row at the same place without the game moving on".
- Suspected cause: `watch_session.py _repeating` applied the tracer's execute-breakpoint rule to every watch kind.
- Impact for the product owner: Find what accesses on a value the game reads in a loop stopped almost at once with a misleading message.
- Status: fixed in the follow-up (only execute stops count); verified, see the re-test section.

### BUG-04: the user guide says guided watches "wait" while a Pro watch runs
- Severity: Low (docs)
- Priority: P3
- Related test case: TC-21, TC-60
- Steps to reproduce: start a Pro watch, then press Lock it / Make it work / Find the real one in the main window.
- Expected result (docs/user-guide.md 10.3): "While a Pro watch runs, Lock it, Make it work and Find the real one wait (and the other way round)."
- Actual result: they are refused at once with "The debugger is in use by Pro's Watch tab. Wait until it's done, or stop it there." (`DebuggerInUse`), and a Pro Start while a guided watch runs is refused the same way. Find it next time and Bring them over (`prove_slot`, `find_hooks`) are refused too but aren't named.
- Suggested wording: "...can't start (they say the debugger is in use) until it ends, and the other way round. The same goes for Find it next time and Bring them over."
- Impact for the product owner: a player waiting for Lock it to "carry on" will wait for nothing.

### BUG-05: a new game during a watch leaves the old game's watch list and results
- Severity: Low
- Priority: P3
- Related test case: TC-43 | Automated test: `test_bug05_a_new_game_during_a_watch_clears_the_old_games_list`
- Steps to reproduce: 1. Start a watch on a heap address. 2. Close the game and start another (or Refresh onto a new PID) while it runs. 3. The watch stops.
- Expected result: as when no watch runs (`game_state_changed(new_game)` clears targets and rows), the old game's list goes.
- Actual result: the clear is skipped because `watching` is still true when the new game arrives, and `_ended` doesn't clear later. The old addresses stay listed; Start would watch them in the new game, and Make cave/NOP entry here computes an offset against the new game's module base.
- Suspected cause: `ui/pro/watch_tab.py game_state_changed` (`if new_game and not self.watching`) with no follow-up in `_ended`.
- Impact for the product owner: confusing leftovers; a cheat entry could be made at the wrong instruction of the new game (it is only written when the player turns it on, and the site check shows the bytes).

### BUG-06: step-16 implementation notes still describe the old behaviour

## Not tested / risks

- **Real PS5 / NG:** dial-back timing, `VERSION` keep-alive on the debugger socket, four slots, DR6, the status field (C-P3a to C-P3e, S-P1/S-P2).
- **Windows `SO_EXCLUSIVEADDRUSE`:** not runnable here. Risk worth a console check: on Windows, an exclusive listener's port can stay unusable while an accepted connection on it is in TIME_WAIT. If the PC closes the back channel first, a second watch started right after the first may get "Port 755 is in use by another program". Suggest adding "Start a second watch right after the first ends" to C-P3a.
- **The PyInstaller build** (spec, `_internal/` layout, windowed exe with no stdout): read only. The spec comment says NOTICE goes "next to the exe"; PyInstaller 6 puts datas in `_internal/` (CI checks `_internal\NOTICE`, so the build is right, the comment is loose).
- **The back-channel listener accepts any peer on the LAN**, not only the PS5's IP: a stray connection on 755 during attach would be taken as the dial-back. Low risk on a home network; noted for the design.
- **Keep-alive vs a stop arriving at the same moment** (AC-11.2 "never while a thread is stopped"): the check and the ping aren't atomic, so one VERSION can go out just as a stop arrives. Harmless on NG as far as we know; not reproducible deterministically.
