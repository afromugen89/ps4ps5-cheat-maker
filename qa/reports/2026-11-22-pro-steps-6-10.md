## Product owner summary

**What I tested:**
- The cave assembler: error line numbers (including Windows line ends and macros), the number rules, the dialect shim, the timeout, a missing or broken assembler, and odd assembler output.
- Turning cave bytes back into text: 24 odd encodings plus bytes that don't decode.
- Turning Pro cheats on and off on FakeConsole: order, read-back, rollback, overlap, enabling twice.
- Live variables.
- Saving Pro cheats through My cheats: rename, delete, Combine, restart, two cheats.
- Bring them over for Pro cheats.
- Import of json/shn/mc4 and Convert to assembly.
- Guided regressions: carry, find_again, and the full suite.

**Verdict:** the core works well.
- Every odd encoding round-trips byte for byte, with `db` lines where NASM would pick another encoding.
- Turning a cheat on writes cave, then jump, then other entries, and reads each back. A failed read-back puts everything back, last write first. Turning it off restores the jump, waits, then zeroes the cave.
- Overlap is refused by name, and live variables write only their own bytes.
- Import keeps bytes exact in all three formats, and Convert re-assembles to the same bytes.

But there are three ways that can put **wrong bytes into the game's code**, and two of them come from the version-update flows.

**Bugs:** 0 Critical, 3 High, 4 Medium, 2 Low.

- BUG-01 (High): a module address written as anything other than exactly `[N]` is assembled as an absolute address. This includes `[0x5e15000+0x40a]`, `[dword N]`, `[N+rcx*4]`, `0b`/`_` numbers, and even out-of-module sums. The cave then reads a low address that isn't mapped, and the game crashes when the cheat is on. Nothing is refused.
- BUG-07 (High): after Bring them over, if the old version's Pro cheat is still in My cheats (same id), the next save overwrites the moved cheat in the new notes with the old offsets. Ticking it after a restart writes into the wrong place in the new game version.
- BUG-08 (High): "Update for this version" moves a Pro cheat's lines but keeps its old Pro source. The old source is saved into the new version's notes and restored at the old offsets.
- BUG-04 (Medium): if NASM's output isn't valid text in the PC's encoding, the assembler raises UnicodeDecodeError instead of reporting an error line. NASM repeats a non-ASCII name the user typed, so on a Windows code page this can crash the editor while typing.
- BUG-05 (Medium): a cave marked "stale" can't be turned on in Pro, but it is still compiled into My cheats and exported to cheat files, with the old variable addresses.
- BUG-06 (Medium): after the editor's save was refused for lack of room, changing a variable assembles the refused source and stores a cave bigger than its room. That cave then goes into the cheat file, over whatever follows it.
- BUG-03 (Medium, security): cave source can pull any file on the PC into the cave (`incbin`, `%include`). A shared `.cmproj` could copy a private file into the cheat file someone then shares.
- BUG-02 (Low): the shim rewrites `[N]` inside strings (`db "[5]"`) and after a spaced segment prefix (`fs: [0x28]` becomes RIP-relative).
- BUG-09 (Low): a stale cave stays stale after Bring them over, even though it was just re-assembled.

**Release recommendation (first round, superseded by the re-test): ❌ Not ready.** BUG-01, BUG-07 and BUG-08 can each corrupt game code on the console. All three have small, local fixes:
- BUG-01: refuse or convert every bare-number memory operand.
- BUG-07: `restore`/`store` must prefer the brought-over source, or the old row must be dropped.
- BUG-08: the updater drops or moves `Cheat.pro`.

The rest can follow.

## Scope

In scope: steps 6-10 as listed above. The UI that calls build/enable/set_variable is step 12 and isn't built yet, so those were driven through the core API. Persistence, rename, delete, Combine, restart and adopt_carried ran through the real MainWindow.

Out of scope: the Pro window (steps 11+), Windows-only behaviour (process start, antivirus, code pages; BUG-04 was simulated), real-console writes (C-P tests), and how CheatRunner treats on == off cave lines (S-P8).

## Bugs

### BUG-01: Module addresses not written exactly as `[N]` are assembled as absolute addresses
- Status: **Fixed in `6c7c726`, verified 2026-11-22.** The bypasses found in the re-test are BUG-10.
- Severity: High (the cave reads or writes an unmapped low address, so the game crashes when the cheat is on)
- Priority: P1
- Related test case: TC-03 | Automated test: `tests/qa/test_pro_steps_6_10_qa.py::test_bug01_every_bare_number_address_is_a_module_offset_or_refused` (6 cases)
- Environment: 08647c5, NASM 2.16.01
- Steps to reproduce: `NasmAssembler(nasm).assemble("mov eax, [0x2000+0x10]", CaveContext(0x1000, 0x100, b"...", module_size=0x10000))`
- Expected result: per the decision, bare numbers are module offsets, so this is RIP-relative to +0x2010. A form that can't be RIP-relative (`[N+rcx*4]`) or is outside the module (`[0x10000+0x10000]`) is refused with a line error.
- Actual result:

  | Source | Assembled as |
  |---|---|
  | `[0x2000+0x10]` | `8b042510200000` = `mov eax,[2010h]` (absolute) |
  | `[dword 0x2010]`, `[0b10000000010000]`, `[0x20_10]` | the same |
  | `[0x2010+rcx*4]` | `mov eax,[rcx*4+2010h]` |
  | `[0x10000+0x10000]` | `[20000h]`, not refused |
- Suspected cause: `core/pro/asm.py` `_PLAIN_ADDRESS` / `_NUM` only match a single literal in `0x`, `h` or decimal form. `check_numbers` uses the same regex, so it misses these forms too.
- Impact for the product owner: a cave that looks right in the editor crashes the game the moment it is turned on.

### BUG-02: The shim rewrites `[N]` inside strings and after a spaced segment prefix
- Status: **Fixed in `6c7c726`, verified 2026-11-22.**
- Severity: Low
- Priority: P3
- Related test case: TC-04 | Automated test: `::test_bug02_shim_leaves_segment_operands_and_strings` (2 cases)
- Steps to reproduce:
  - `mov rax, fs: [0x28]` becomes `64 48 8b 05 20 f0 ff ff` (`fs:[rip+...]`) instead of `64 48 8b 04 25 28 00 00 00`.
  - `db "[5]"` becomes the bytes of `[rel $$+(0x5-0x1000)]`.
- Expected result: segment-prefixed operands are left alone (implementation notes); string contents are unchanged.
- Suspected cause: `_PLAIN_ADDRESS` lookbehind `(?<![:\w])` doesn't allow a space after the colon, and the shim ignores quotes.

### BUG-03: Cave source can read any file on the PC into the cave
- Status: **Fixed in `6c7c726`, verified 2026-11-22.** A bypass found in the re-test is BUG-11.
- Severity: Medium (security)
- Priority: P2
- Related test case: TC-05 | Automated test: `::test_bug03_cave_source_cant_read_pc_files`
- Steps to reproduce: assemble `incbin "/path/to/file"` (or `%include`).
- Expected result: refused. A cave is code the user writes; it has no reason to read PC files.
- Actual result: the file's bytes become the cave bytes. Compile, the `.cmproj` and exported cheat files then carry them. A `.cmproj` from someone else, re-assembled by Bring them over or Build, would pull a private file into a cheat file the user may share.
- Suspected cause: `NasmAssembler` passes the source through unchanged. Refuse `incbin`, `%include`, `%pathsearch` and `%depend` in the shim (and `%!` environment reads).

### BUG-04: Assembler output that isn't valid in the PC's text encoding raises UnicodeDecodeError
- Status: **Fixed in `6c7c726`, verified 2026-11-22.**
- Severity: Medium
- Priority: P2
- Related test case: TC-08 | Automated test: `::test_bug04_undecodable_assembler_output_is_an_error_line`
- Steps to reproduce:
  1. NASM repeats a symbol name as raw UTF-8: ``symbol `ラベル' not defined``.
  2. The output is decoded with `text=True`, i.e. the locale encoding with strict errors.
  3. On Windows code pages, some UTF-8 sequences are invalid; e.g. cp1252 has no 0x81, which is in `あ` = E3 81 82.
  4. A fake assembler that prints `\xff` on stderr reproduces this on Linux.
- Expected result: an error line.
- Actual result: `UnicodeDecodeError` escapes `assemble`.
- Suspected cause: `core/pro/asm.py` `subprocess.run(..., text=True)`. Use `encoding="utf-8", errors="replace"`.
- Impact for the product owner: typing a non-English name in the cave editor can crash the window (step 12 assembles on every pause in typing).

### BUG-05: A stale cave is still compiled into My cheats and cheat files
- Status: **Fixed in `6c7c726`, verified 2026-11-22.**
- Severity: Medium
- Priority: P2
- Related test case: TC-25 | Automated test: `::test_bug05_stale_cave_isnt_exported`
- Steps to reproduce:
  1. Take a cheat with two caves; the second uses the home cave's variable.
  2. Grow the home cave so the variables move, while the second cave fails to re-assemble (e.g. a timeout).
  3. The second cave is now `stale`.
  4. Call `compile_cheat(pc)`, then `CheatFile.saveable_cheats()`.
- Expected result: the decision says a stale cave can't go on until it is rebuilt, so it shouldn't reach My cheats or a cheat file either.
- Actual result: the cheat is compiled and exported (badge CheatRunner), and its second cave reads the variables' old addresses. Only `compile.enable` checks `stale`; the guided turn-on in My cheats and the export don't.
- Suspected cause: `core/pro/compile.py` `compile_cheat` (and `refresh`/`restore`) ignore `ProEntry.stale`.

### BUG-06: set_variable stores a cave bigger than its room after the editor's save was refused
- Status: **Fixed in `6c7c726`, verified 2026-11-22.** A related layout problem is BUG-12.
- Severity: Medium
- Priority: P2
- Related test case: TC-26 | Automated test: `::test_bug06_set_variable_never_grows_a_cave_past_its_room`
- Steps to reproduce:
  1. Build a cave. Something sits 64 bytes later, so the room is 48 bytes.
  2. Set `entry.source` to a 112-byte source; `build` raises NoRoom, which is correct.
  3. Call `set_variable(pc, "mult", 3.0, ...)`.
- Expected result: the stored bytes stay within the room (NoRoom, or the built source is used).
- Actual result: it returns "saved", and `entry.cave_bytes` is now 112 bytes. `compile_cheat` exports it over whatever follows the cave.
- Suspected cause: `compile.set_variable` re-assembles `entry.source` (which may be unbuilt) and stores the result with no `room_at` check. The existing test `test_variable_change_that_moves_code_asks_for_a_restart` even sets up an "edited, not rebuilt" source and expects the new bytes to be stored.

### BUG-07: After Bring them over, the old Pro cheat in My cheats overwrites the moved one
- Status: **Fixed in `6c7c726 (merge case: e885877)`, verified 2026-11-22.**
- Severity: High (wrong offsets in the new version's notes; the guided turn-on writes without checking)
- Priority: P1
- Related test case: TC-32 | Automated test: `::test_bug07_bring_over_result_isnt_overwritten_by_the_old_row`
- Steps to reproduce:
  1. A Pro cheat (id p1) is in My cheats for version A.
  2. The game is now version B and Bring them over moves p1, e.g. from +0x100/+0x300 to +0x140/+0x340.
  3. The Controller keeps the cheat file when the title is unchanged.
  4. `find_again.adopt_carried(project, found)` calls `restore`. Restore skips p1 because My cheats already holds a cheat with that id, so the moved cheat is never listed.
  5. `save()` then calls `store`, which replaces the project's p1 with the old in-memory source.
- Expected result: the moved p1 (+0x140/+0x340) is in My cheats and in the saved notes.
- Actual result: the saved notes hold p1 at +0x100/+0x300 (test output `[256, 768] != [320, 832]`). After a restart it comes back at the old offsets with no version warning, and ticking it writes the jump and NOPs into the wrong place in version B.
- Suspected cause: `compile.restore` dedups by id only, and `compile.store` replaces by id. Brought-over cheats need to replace the stale rows, or rows from another version must be dropped before restore and store.

### BUG-08: "Update for this version" keeps the old Pro source on the moved cheat
- Status: **Fixed in `6c7c726`, verified 2026-11-22.**
- Severity: High
- Priority: P1
- Related test case: TC-33 | Automated test: `::test_bug08_update_for_this_version_keeps_source_and_lines_together`
- Steps to reproduce:
  1. Take a Pro cheat with a NOP entry at +0x300, compiled into the cheat file.
  2. Run `up.update_file` to a version where the code moved by 0x40. The cheat is reported moved, and its line is at +0x340.
  3. Call `store` into the new version's project, then `restore`.
- Expected result: the source and the lines agree (the source is moved too, or dropped).
- Actual result: `moved.pro` is the very same old ProCheat (+0x300). The restored cheat writes at +0x300.
- Suspected cause: `core/updater.py` `update_file` uses `dataclasses.replace(c, locations=...)`, which keeps `pro`. Then `find_again.save` stores it into the new notes.
- Note: a Pro cheat with a cave doesn't move by this flow at all: its cave line has on == off, so it is treated as a patch and reported as "code at +1F00 not found". Bring them over is the way for those, but the report message is confusing.

### BUG-09: A stale cave stays stale after Bring them over
- Status: **Fixed in `6c7c726`, verified 2026-11-22.**
- Severity: Low
- Priority: P3
- Related test case: TC-41 | Automated test: `::test_bug09_bring_over_clears_stale`
- Actual result: `bring_one` re-assembles every cave at its new place but copies `stale=True` from the old entry. Pro then refuses to turn the moved cheat on until it is rebuilt again.
- Suspected cause: `refpoints._place` doesn't reset `entry.stale`.

## Observations (not filed)

- Cave sources accept `bits 32` and `section .data`, which give 32-bit code or a split layout (labels in `.data` aren't in the map). These are the user's own choice, but the editor could warn.
- Instruction names (`add`, `mov`, `nop`) are allowed as variable names. They assemble correctly as labels with NASM 2.16.01.
- The guided turn-on (`freezer.set_once`) writes a cheat's bytes without checking its off-bytes. This is pre-existing, and it is what turns BUG-07 and BUG-08 into wrong writes rather than refusals.
- After `Combine`, the Pro cave's room is no longer reserved through `pro_cheats`; the combined row's code lines are still in My cheats and keep guided caves out via open rooms.

## Not tested / risks

- Windows: NASM start time and antivirus against the 2 s timeout (AC-8.1 measured on Linux only), code pages (BUG-04 simulated), `CREATE_NO_WINDOW`.
- The step 12 editor and dialogs: whether they keep `entry.source` and `cave_bytes` consistent, which matters for BUG-06.
- Real console: NG writes crossing 0xFF (AC-8.6 is logic only), and CheatRunner on on == off cave lines (S-P8).

## BUGS FOR FEATURE-IMPLEMENTOR

1. **BUG-01 (High)**: bare-number addresses other than the exact `[N]` form are absolute and never refused.
   - Repro: `assemble("mov eax, [0x2000+0x10]", CaveContext(..., module_size=0x10000))`.
   - Expected: RIP-relative to +0x2010, or a line error.
   - Actual: `8b042510200000`. The same happens for `[dword N]`, `[0b..]`, `[0x20_10]`, `[N+rcx*4]` and `[0x10000+0x10000]`.
   - Make pass: `tests/qa/test_pro_steps_6_10_qa.py::test_bug01_every_bare_number_address_is_a_module_offset_or_refused`.
   - Cause: `core/pro/asm.py` `_PLAIN_ADDRESS` / `_NUM` / `check_numbers`. Consider refusing any memory operand with no base register other than the exact forms, or checking the assembled bytes with iced: any absolute or base-less disp32 operand not from `[abs N]` is an error.
2. **BUG-07 (High)**: after Bring them over, the old Pro row in My cheats overwrites the moved cheat in the new notes.
   - Repro: an old compiled p1 is in the cheat file, then `finder.adopt_carried(project_with_moved_p1, {})`.
   - Expected: the saved p1 offsets equal the moved ones.
   - Actual: the old offsets are saved.
   - Make pass: `::test_bug07_bring_over_result_isnt_overwritten_by_the_old_row`.
   - Cause: `compile.restore` (dedups by id) and `compile.store` (replaces by id), called from `find_again.adopt_carried` / `save`.
3. **BUG-08 (High)**: Update for this version keeps `Cheat.pro` at the old offsets.
   - Repro: `up.update_file` on a compiled Pro cheat, then `store` and `restore`.
   - Expected: the source matches the moved lines (or `pro` is dropped).
   - Actual: the restored cheat is at the old offsets.
   - Make pass: `::test_bug08_update_for_this_version_keeps_source_and_lines_together`.
   - Cause: `core/updater.py` `update_file`, `replace(c, locations=...)`.
4. **BUG-04 (Medium)**: UnicodeDecodeError from the assembler's output.
   - Make pass: `::test_bug04_undecodable_assembler_output_is_an_error_line`.
   - Fix: decode NASM's output as UTF-8 with `errors="replace"` (`core/pro/asm.py`, `subprocess.run`).
5. **BUG-05 (Medium)**: a stale cave is compiled and exported.
   - Make pass: `::test_bug05_stale_cave_isnt_exported`.
   - Cause: `compile.compile_cheat` / `refresh` / `restore` ignore `stale`.
6. **BUG-06 (Medium)**: `set_variable` stores an unbuilt or oversized cave.
   - Make pass: `::test_bug06_set_variable_never_grows_a_cave_past_its_room`.
   - Cause: `compile.set_variable` (no `room_at` check; assembles an unbuilt source).
7. **BUG-03 (Medium, security)**: `incbin` / `%include` read PC files.
   - Make pass: `::test_bug03_cave_source_cant_read_pc_files`.
   - Fix: refuse those directives in the shim or wrapper.
8. **BUG-02 (Low)**: the shim rewrites inside strings and after `fs: `.
   - Make pass: `::test_bug02_shim_leaves_segment_operands_and_strings`.

   - Make pass: `::test_bug09_bring_over_clears_stale`.

### BUG-10: The absolute-operand check can still be skipped
- Severity: Medium (the same outcome as BUG-01: an unmapped low address is read, so the game crashes when the cheat is on)
- Priority: P2
- Related test case: TC-03d | Automated test: `tests/qa/test_pro_steps_6_10_qa.py::test_bug10_absolute_operand_check_cant_be_skipped` (3 cases)
- Environment: e885877, NASM 2.16.01
- Steps to reproduce (each assembles to `8b 04 8d 10 20 00 00` = `mov eax,[rcx*4+2010h]`, with no error):
  1. `mov eax, [0x2010+rcx*4] ; take abs`: the word "abs" in the comment.
  2. `times 1 mov eax, [0x2010+rcx*4]`: the line is treated as a data line.
  3. `%line 0+1 other` then `mov eax, [0x2010+rcx*4]`: later rows are no longer in the "user" region.
- Expected result: refused, as for the same operand without these.
- Suspected cause: `core/pro/asm.py` `absolute_operand`:
  - `re.search(r"\babs\b", row.text)` looks at the whole listing text, comment included.
  - `_DATA_WORDS` skips any row starting with `times`.
  - `parse_listing` trusts `%line` directives written in the user's source.
- Suggested fix: strip the comment (`split_line`) before looking for `abs`. Decode the bytes of `times` rows. Refuse `%line` in user source, or decode every row of the cave except `db`-style rows.
- Note: `ea-absolute` alone doesn't catch an indexed absolute operand, so the iced check is the only guard for these forms.

### BUG-11: `incbin` built with `%[...]` still reads PC files
- Severity: Medium (security; same impact as BUG-03)
- Priority: P2
- Related test case: TC-05d | Automated test: `::test_bug11_incbin_built_with_token_pasting_is_refused`
- Steps to reproduce: `%define IB incb` then `%[IB]in "/path/secret.txt"`.
- Expected result: refused.
- Actual result: the file's bytes are the cave.
- Suspected cause: the deny-list matches source text, but the preprocessor can build the word with `%[...]`, `%xdefine` + `%[]`, and so on.
- Suggested fix: refuse `%[` as well (with `%+` and `%deftok` it is the token-building route). Or more robustly, check the NASM listing or preprocessed output (`-E`) for `incbin` and `%include`. Or run NASM with an include path that holds nothing and a cwd it can't escape: `-I` doesn't stop absolute paths, so the preprocessed check is the solid one.

### BUG-12: Adding or retyping a variable, then a failed build, makes set_variable write into the cave's code
- Severity: High (with the cheat on, the bytes of the cave's `jmp return` are overwritten live, so the game jumps to a wild address)
- Priority: P1 for step 12 (no UI reaches it yet)
- Related test case: TC-26c | Automated test: `::test_bug12_set_variable_uses_the_built_layout`
- Steps to reproduce:
  1. Build a cheat with `mult: float` and turn it on.
  2. Append `Variable("n", INT32, 1)` to `pc.variables`, as the editor's variables table would.
  3. Build again; the assembler refuses (a typo).
  4. Call `set_variable(pc, "mult", 5.0, on=True)`.
- Expected result: the value goes to `mult`'s built place (the last 4 bytes), or the change is refused until the cave is built.
- Actual result: `variable_offsets(pc.variables, len(cave_bytes))` places `mult` 4 bytes earlier, assuming `n` is already in the cave. The live write `0000a040` lands at cave+8, over `e9 0a e2 ff ff` (the jump back): built `…e90ae2ffff00000000 40` becomes `…e90a0000a040 00000040`.
- Suspected cause: `core/pro/compile.py` `set_variable` (and `compile_cheat`'s `value_at`, used by My cheats' value box) derive variable offsets from the current `pc.variables`, not from the layout the cave was built with. Before the fix the re-assembly kept them in step.
- Suggested fix: record the built variable layout (names, types, offsets) on the home entry at build time, and use it in `set_variable` / `compile_cheat`. Refuse with "build the cave first" when the list differs.
